# Release Verification Checklist

**Purpose:** record evidence for the remaining paper-order lifecycle release gates without implying that CI alone proves production safety.

**Scope:** paper/shadow execution only. This checklist does not authorize live trading, deployment, or changes to a production database. Run the database rehearsal only against an explicitly authorized, isolated copy of a representative deployed-schema snapshot.

Record before testing:

- [ ] Candidate commit SHA:

- [ ] No production credentials or production database endpoint are configured:
- [ ] Test outputs and logs are stored without credentials, tokens, or sensitive customer data:

**Stop immediately** if the environment cannot be distinguished from production, snapshot authorization is missing, the restore plan is unverified, or the test might submit a real order. Do not make the checklist green based on assumptions.

## Gate 1 — Automated CI evidence

- [ ] Required PR checks passed on the exact candidate commit.
- [ ] MariaDB integration job passed, not merely skipped.
- [ ] The test report confirms the migration tests ran against disposable test databases.
- [ ] No unexplained test failures, retries masking failures, or unreviewed skips remain.

Evidence: link the CI run and record the exact commit SHA. CI passing is necessary, not sufficient, for release verification.

## Gate 2 — Populated-schema migration rehearsal

Follow [Populated Database Migration Rehearsal](POPULATED_DATABASE_MIGRATION_REHEARSAL.md).

- [ ] Record pre-migration schema/migration versions.
- [ ] Record row counts and stable checksums or equivalent comparisons for representative historical OHLCV data.
- [ ] Run the documented migration path against the isolated snapshot.
- [ ] Confirm all expected migrations are applied exactly once and checksums are consistent.
- [ ] Confirm historical OHLCV rows are unchanged.
- [ ] Confirm representative existing application tables and indexes remain usable.
- [ ] Restart the application against the rehearsed database and inspect startup/migration logs.
- [ ] Repeat the documented status/dry-run operations and confirm they do not mutate the schema or data.
- [ ] Record any differences and investigate before proceeding.

Evidence must identify the snapshot (without exposing secrets), candidate SHA, migration output, before/after comparisons, and test outcome. A fresh empty database does not satisfy this gate.

## Gate 3 — Paper order lifecycle smoke and recovery

Use only disposable data and the existing lifecycle test procedures in [Paper Order Lifecycle](PAPER_ORDER_LIFECYCLE.md).

- [ ] Create a paper order and verify the durable intent is visible in history.
- [ ] Verify a successful simulated fill creates one position and one ledger transition, without duplicate fills on retry.
- [ ] Verify cancellation before fill prevents a later fill.
- [ ] Exercise cancel-versus-fill race and verify the final state is internally consistent.
- [ ] Simulate process interruption at the documented recovery point; restart and verify pending orders recover without duplicate positions.
- [ ] Simulate a failed transaction and verify rollback leaves no partial fill/position state; retry safely.
- [ ] Verify unauthorized users cannot access or mutate protected order operations.
- [ ] Verify the emergency stop blocks new entries while preserving safe handling of existing paper positions.

Record order IDs generated by the test, expected/actual state transitions, and relevant sanitized logs. Do not use real funds or exchange credentials.

## Gate 4 — Manual dashboard and accessibility checks

Run on the candidate build in a browser. Automated tests do not complete this gate.

- [ ] Sign in and navigate to order history using only the keyboard.
- [ ] Verify visible focus, logical tab order, and no keyboard traps.
- [ ] Open and close dialogs; verify focus enters the dialog and returns to the invoking control.
- [ ] Operate order filters and cancellation controls with keyboard only.
- [ ] Verify loading, empty, error, cancellation, and filled states are understandable without relying on color alone.
- [ ] With a screen reader, verify page/section headings, table headers, row context, button names, and status announcements.
- [ ] Verify sort/filter changes announce useful context and do not unexpectedly move focus.
- [ ] Check narrow mobile viewport, 200% zoom/reflow, and forced-colors/high-contrast mode.
- [ ] Check reduced-motion preference and ensure essential feedback is still available.
- [ ] Confirm error messages are actionable and do not expose secrets or internal connection details.

Record browser/OS, screen reader and version, viewport/zoom, each result, and reproducible defects. Mark unsupported checks as **not run**, not passed.

## Gate 5 — Decision

- [ ] Gates 0–4 have evidence and no unresolved release-blocking defect.
- [ ] Any exception has a named owner, rationale, risk acceptance, and expiry/revisit date.
- [ ] Reviewer other than the tester has reviewed the evidence.

Decision: **HOLD** until every mandatory gate is evidenced. Passing CI or completing this document does not itself authorize deployment. Deployment and any production database operation require separate explicit authorization.
