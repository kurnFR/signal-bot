# P0.3 — Paper Position Sizing & Accounting

## Status

**Application integration implemented. Runtime/database verification remains required before the P0.3 gate is closed.**

## What changed

`db/migrate_p0_paper_accounting.sql` adds explicit accounting fields to `paper_positions` and `paper_trades`:

- allocated capital
- risk per trade
- risk amount
- stop distance
- quantity
- notional value
- entry/exit fees
- funding P&L
- gross/net P&L on the closed-trade ledger

It also adds a generated key and unique index for OPEN positions so the database itself rejects duplicate active positions for the same symbol/market/timeframe/strategy.

## Application integration

`paper/engine.py` now:

1. Sizes every new paper position through `backtest.accounting.calculate_position_size()`.
2. Persists risk amount, stop distance, quantity and notional value.
3. Persists entry fee at position creation.
4. Uses `backtest.accounting.calculate_trade_accounting()` for realized gross P&L, fees, net P&L and R.
5. Looks up recorded futures funding events over the position holding interval.
6. Applies funding with the correct LONG/SHORT sign convention.
7. Persists canonical `gross_pnl`, `entry_fee`, `exit_fee`, `funding_pnl`, `net_pnl`, and `r_multiple`.
8. Uses compare-and-set status updates so repeated close attempts are idempotent.
9. Treats the database duplicate-position constraint as an expected concurrent-sync outcome.
10. Removes the import-time database mutation from `seed_validated_paper_configs()`.

## Position sizing contract

For a normal spot position:

`risk_amount = allocated_capital × risk_per_trade_pct / 100`

`stop_distance = abs(entry_price - stop_loss)`

`quantity = risk_amount / stop_distance`

`notional = quantity × entry_price`

For futures, the same price-risk sizing model applies. Leverage/margin constraints must be applied separately; leverage must never silently increase the allowed risk amount.

## Funding contract

The engine reads `funding_rate(symbol, event_time, mark_price, funding_rate)` rows strictly after entry and through exit. The canonical helper treats positive funding as a LONG cost; the SHORT position receives the inverse sign.

## Remaining P0.3 verification gate

The implementation is not considered production-verified until the environment confirms:

- the P0 schema migration has been applied;
- an active paper position receives the expected quantity/notional/risk fields;
- a closed position produces the same accounting result as the canonical accounting regression tests;
- futures positions accrue funding from stored funding events;
- duplicate sync attempts do not create a second OPEN position.

## Important P0.5 boundary

The engine still uses the existing strategy runner's latest-bar discovery path. That path is intentionally **not** declared execution-parity complete. The next step is to implement the explicit:

`SIGNAL -> PENDING_ENTRY -> ACTIVE -> CLOSED`

lifecycle so a signal detected on a closed candle is never retroactively filled at a bar that has already opened.
